# Rules for coding agents in UPbRPy

UPbRPy is a Python LA-ICP-MS U-Pb and trace-element reduction engine
(`UPbRPy/`) with an optional PySide6 + pyqtgraph desktop GUI, UPbRPy Studio
(`GUI/`). It belongs to Yiming Zhang's open-source lab workflow (with
UPbDB, upbstudio, grainatlas and bracketeer, each in its own repository).

## Current work

The input-layer restructure for Qtegra exports. As of 2026-11-05 the UPbR
CSV is dropped, reduced Rich files are accepted, the public data model is in
`docs/data-model/` (MkDocs, `make docs`; keep it true when you change a
reader, and keep `tests/test_data_model_docs.py` passing), S513 and LTSE are
in the reference library, and Studio opens projects as tabs
(`GUI/studio_window.py`). Read these two first:

- `docs/qtegra_export_formats.md`: the decision and the contract (which export
  is canonical, the in-memory model, the readers, the rules every consumer
  follows).
- `docs/qtegra_input_plan.md`: the milestones, the exact API, and the design
  decisions already taken. Do only the milestone your brief names.

## House rules

- **Never run git commands that change state** (no commit, add, stash, reset,
  checkout, branch, tag, push). The supervising session owns git.
- Do not touch files you were not asked to change. In particular leave
  `GUI/theme.py`, `GUI/icon.py`, `GUI/assets/` alone: they hold the owner's
  uncommitted work.
- Never modify or move anything under `tests/fixtures/qtegra/`; it is
  generated by `scripts/make_qtegra_fixture.py` from the real session, and its
  CSV files keep CRLF line endings and a BOM on purpose.
- Real data stays on the laptop. Do not add large files; the repository holds
  code and small fixtures only. Do not create package stores, virtual
  environments, caches or build output inside the repository.
- Do not add or change GitHub Actions triggers. CI runs only on `v*` tags and
  `workflow_dispatch`.
- The engine in `UPbRPy/` stays free of Qt, HTTP and database code.
- Existing tests must keep passing unchanged. Add tests for what you build
  under `tests/`.
- Light theme by default; every window must fit a 14-inch MacBook
  (1440x900 and 1280x800 logical pixels).
- Plain, precise docstrings and docs; no marketing language.

## Environment

- Python: `.venv/bin/python` (3.14, a symlink to a cached venv outside the
  repository; it has numpy, pandas, scipy, PySide6, pyqtgraph and pytest).
  Do not pip-install anything; if something is missing, say so.
- Run QUICK after every change with `make test-quick`.
  Run FULL before a Studio build/install or changes to reduction numerics,
  the .upbr format, database submit/link/preferred, conftest or pyproject with `make test`.
  Baseline before this work: 250 passed, 4 skipped.
- Your sandbox cannot show windows. GUI behaviour you cannot test offscreen,
  say so in your final message; the supervisor runs those checks.

## Final message

End every run with: files changed, public API added or changed (names and
signatures), test command and result, and anything you could not do or are
unsure about.

## Performance and scale (server calls)

The lab database is built for many users and very large datasets (millions of
grains, acquisitions and spots) reached over slow networks. Every call this app
makes to it follows these rules:

- **Page, never fetch everything.** Request lists with `limit` and follow the
  `X-Next-Cursor` cursor; show the first page at once and load more on demand.
- **Revalidate, do not re-download.** Keep the `ETag` of each list or detail
  and send `If-None-Match`; a 304 means the cached copy is current. Cache per
  account and server, and clear it on sign-out.
- **Never block the interface on a download.** Fetch progressively, show what
  has arrived, and keep the app usable while the rest loads.
- **Time out on stalls, not on size.** Use a short connect timeout and a stall
  timeout without data; never a short cap on the whole transfer. Accept gzip.
- **No request per row.** Ask for a batch or a summary the server provides;
  if one is missing, say so instead of looping over items.
- **Errors say what happened**: the status and a short excerpt of the reply,
  never only a library message.
- **Measure** request count and time before and after a change that touches
  server calls, and test with a large mocked list (thousands of rows).

## After a major update

Rust and PyInstaller builds fill the disk quickly. Once the work is pushed and
any app built from it is installed in `/Applications` and smoke-tested:

1. Note free space (`df -h /`).
2. Run `make clean-build`. It removes `build/` and the PyInstaller `work/`, `dist/`, `previous-build/` and `previous-dist/` under `~/Library/Caches/UPbRPy/<checkout key>/` (or `$UPBRPY_BUILD_ROOT`); install `dist/UPbRPy Studio.app` first. It keeps the build `venv` in that folder, `.venv`, and the docs venv and site. It stops if a build
   is still writing there, and prints free space before and after.
3. Remove the worktrees and build checkouts you created for this work
   (`git worktree remove`, then `git branch -d` for merged branches).
4. Keep installed apps and review artifacts (screenshots, previews, print
   files, COMMIT notes in `~/Github/lab-builds`). Never touch another
   session's worktree, scratchpad or running build, project data or
   databases.
5. Report free space before and after.
